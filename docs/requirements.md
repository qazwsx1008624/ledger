# 生活费记账本 · 产品需求文档

> 本文是自包含文档，不依赖任何对话上下文，可直接作为实现依据。
> 文末「当前实现状态」标注了哪些已经做完、哪些还没做。

## 1. 背景与目标

用户是一名大学生，需要统计自己的生活费收支情况，纯个人使用。

**用户要解决的问题：**

1. 每天记账，想知道今天花了多少、这个月到目前花了多少
2. 每月想知道钱花在哪些方面（餐饮花了多少、娱乐花了多少）
3. 对比收入与支出，判断这个月能存下多少钱
4. （第二阶段）每月为每个分类设定预期花销，月底对比实际与预期的差距

**明确的产品取向：**

- 数据量很小：一笔一笔记，每天约 4–6 笔，一年约 1500–2000 条。**性能永远不会是问题**，因此全部设计重心放在「录入快」和「统计不出错」上。
- 数据由用户**手工输入**，不导入微信/支付宝账单，不做任何账单解析。
- 数据**不能丢**、**不能算错**。这两条是硬性要求，优先级高于功能丰富度。

## 2. 核心概念与统计口径

这一节是全文档最重要的部分。下面每一条都是**必须由测试守住的不变量**，因为一旦写错，界面上显示的数字看起来仍然完全正常，靠肉眼无法发现。

### 2.1 账目类型有三种，但落地为两个字段

| 类型 | 含义 | 对统计的影响 |
| --- | --- | --- |
| `income` 收入 | 生活费、兼职、奖学金 | 增加收入 |
| `expense` 支出 | 正常消费 | 增加支出 |
| `refund` 退款 | 退货、退款、返现 | **减少**支出 |

实现建议：`kind` 字段只有 `income` / `expense` 两个值，退款作为 `expense` 的一个布尔标记（如 `is_refund`）。这样类型判断简单，且退款天然属于「支出」这一侧。

### 2.2 金额永远存正数「分」

- 金额以 **整数「分」** 存储（字段名如 `amount_cents`），绝不用浮点数。
- **不允许存负数金额。** 方向完全由类型决定（退款靠 `is_refund` 标记表达，不靠负号）。
- 理由：如果同一字段里既有正数又有负数，迟早会出现「负数支出」与「退款」两个含义互相打架，这是算错的经典来源。禁止负数可以从结构上杜绝这类错误。
- 只有在渲染时才把「分」换算成「元」。

### 2.3 必须由测试守住的不变量

| 不变量 | 说明 |
| --- | --- |
| `净支出 = 正常支出 − 退款` | 退款抵扣支出，不是计入收入 |
| `可存下 = 收入 − 净支出` | 界面上展示的核心结论 |
| 支出与分类占比**全部按净额显示** | 某分类花 300、退 300，该分类净额为 0，而不是支出 300 与退款 −300 各占一行 |
| 已软删除的账目**不得计入任何合计** | 每一个统计查询都必须过滤 `deleted_at IS NULL`，漏掉一处就会算错 |
| 金额解析无浮点误差 | 例如 `0.1 + 0.2` 这类问题不得出现 |
| 非法输入不得入库 | 金额必须 > 0、日期格式合法、分类必填 |

**验证示例（可直接作为测试用例）：**

- 记一笔支出 300（餐饮），再记一笔退款 300（餐饮）→ 餐饮净支出必须是 **0**，总净支出必须是 **0**
- 记一笔支出 100，软删除后 → 总净支出必须回到 **0**
- 退款不得出现在收入合计里
- 金额输入 `0`、`abc`、`-5`、`1.234` 都必须被拒绝

### 2.4 日期与月份归属

- 日期格式 `YYYY-MM-DD`，按**本地时区**计算今天（不能用 `toISOString()`，会有时区偏移导致日期串档）。
- 月份归属完全由账目的 `date` 字段决定。
- **录入时点口径**：按「消费发生的那一天」记录，不按还款日记录。用户若使用花呗/白条，应记在消费当天。这条不靠代码强制，但文档与界面提示需要说明，否则月度统计会整体错位。

## 3. 功能需求

### 3.1 记账录入（最高优先级）

每天使用 4–6 次，**录入速度决定这个产品会不会被用下去**。

字段：日期、类型（收入/支出）、金额、分类、备注。

要求：

- **打开即默认「今天 + 支出」**，光标直接落在金额输入框，不需要点任何地方。
- **金额敲完按回车即保存**，不需要鼠标点击。
- 分类用**一排按钮**呈现，点击即选中，不用展开下拉框。
- 日期默认今天，旁边提供**「昨天」「前天」快捷键**（补账是常态）。
- 保存后：表单清空、光标回到金额框，可以连续记下一笔。
- 保存后立即显示**「已记在 X 月 X 日」**，让用户有机会发现日期错误。
- **最近 3 笔**直接显示在录入区附近，带编辑与删除按钮。记错通常发生在刚记完的几秒内，不需要去列表里翻。
- 备注选填，但留空时给轻微提醒（哪怕写两个字也远好过留空，否则事后无法回想）。

**必须防止的错误：**

- **重复提交**：保存后按钮立即禁用，写入前再次校验，避免一笔账变两笔。
- 非法输入在提交前就被拦下并给出明确提示。

### 3.2 账目修改与删除

- **所有字段都可改**：日期、金额、分类、备注、类型（支出记成收入也能改回来）。
- **软删除**：删除写入 `deleted_at`，不物理删除。
- 删除时二次确认。
- 删除后显示**「已删除，撤销」提示条**，几秒内可点回。
- 另有回收站页面，可查看与恢复已删除账目。

### 3.3 分类管理

用户要能自己增删改分类，因为实际分类会随生活变化调整。

- 支持新增、重命名、删除、调整顺序。
- **重命名时历史账目跟着走**，不得出现账目停留在旧名称、统计里凭空多出一行的情况。
- 删除分类时需明确提示该分类下还有多少笔账目，以及这些账目将如何处理（建议：不允许删除仍有账目的分类，或要求先迁移到其他分类）。
- **收支分类名不允许重复**（历史缺陷：原先的筛选逻辑按分类名匹配，收支下若同名会同时命中。约束分类名在全部收支中唯一可以从根本上避免这类问题）。

**预置分类（按大学生活费场景）：**

| 类型 | 分类 |
| --- | --- |
| 支出 | 饮食、日用、水电通讯、交通、购物、娱乐、学习、医疗 |
| 收入 | 家人生活费、兼职、奖学金 |

预置分类仅首次建库时写入，之后不覆盖用户改动。

### 3.4 「用途待补充」标记与快捷分类

**需求来源：** 手写记账时会出现「忘了这笔钱是干什么的」。用户需要一个地方标记这类支出，并在之后想起来时**快速**补上分类。

设计要求——**它不是一个普通分类，而是一个「待补充」状态**：

- 录入时可以标记为「用途待补充」。
- 统计表中它**单独列在最后一行**，与正常分类区分开。
- 主界面显示 **「有 N 笔用途待补充」**，点击进入快捷分类界面。
- 它**照常计入总支出**（钱确实花了），只是分类占比里被标出来。
- 核心目的：把「忘了」变成一个会自己提醒你的**待办事项**，而不是一个无声堆积的分类。否则它会在分类占比里长成没有信息量的一大块，稀释统计的价值。

**快捷分类界面（逐笔过）：**

```
┌─────────────────────────────────────┐
│  用途待补充                    2 / 3 │
│                                      │
│          ¥ 32.00                     │
│      10-14 周二 · 无备注              │
│                                      │
│   [1] 饮食   [2] 日用   [3] 水电通讯  │
│   [4] 交通   [5] 购物   [6] 娱乐      │
│   [7] 学习   [8] 医疗                │
│                                      │
│              [ 还是想不起来 ]         │
└─────────────────────────────────────┘
```

- **排序：金额从大到小。** 大额消费印象更深，先清掉收益最大。
- 显示每笔的**金额（要大）、日期、已有备注**。金额是唤起记忆的关键线索。
- **按数字键 1–9 立即归类并自动翻到下一笔**，全程不碰鼠标，一笔一次按键。
- **必须提供「还是想不起来」出口**（`Esc` 或空格跳过，留在待补充里）。没有出口会迫使用户瞎选一个分类，那比留空更糟——它变成了一条看似正常的错误数据。
- 分类超过 9 个时，数字键覆盖前 9 个（用户可调整顺序），其余用鼠标点选；不引入 `Ctrl+数字` 组合键。

### 3.5 统计

统计全部通过 SQL 聚合得出，**不得把明细拉到前端累加**（分页或筛选时会算漏）。

**每日（显示在主页面，不需翻页）：**

- 今日支出
- 本月累计支出
- 本月剩余天数「平均每天可用」

「平均每天可用」的口径：

- **尚未设定月度预期时**：显示**本月日均支出**（本月已花 ÷ 已过天数），让用户了解当前节奏。
- **已设定月度预期后**：显示**剩余每天可用** = `(预期总额 − 本月已花) ÷ 剩余天数`（剩余天数含今天）。
- 本月已结束时需处理除零情况。

**每月：**

- 收入、净支出、退款（单列一行）、可存下（收入 − 净支出）、笔数
- **分类占比排行**，以表格呈现：分类、金额、占比、笔数。要求能一眼看出「餐饮花了多少、娱乐花了多少」。
- 建议同时给出与上月的对比（差多少、差百分之几），这是判断「这个月有没有失控」最直接的信息。

**刻意不做：** 图表库与饼图。按金额排序的表格加百分比条读起来更快，且不需要引入额外依赖。

### 3.6 数据安全（硬性要求）

用户明确要求「不能丢数据」。浏览器存储**无法做到绝对不丢**，因此必须靠以下多层设计把风险降到最低：

**a) 自动备份到真实文件夹**

- 使用 File System Access API 让用户选择一个备份目录（只需选一次，目录句柄可持久化保存）。
- 数据每次变动后自动写入一份备份文件到该目录。
- **仅 Chrome / Edge 支持**（Firefox 不支持该 API）。不支持时退回「提醒用户手动导出」。
- 需注意浏览器可能要求重新授权目录访问权限，要有处理该情况的流程。

**b) 启动一致性检查（防「静默丢失」的关键）**

- 维护一份备份清单，记录每次备份的时间与**账目笔数**。
- 应用启动时对比：本地数据库笔数 vs 备份清单记录的笔数。
- 若**本地为空（或明显少于备份）而备份中有记录**，说明浏览器清除了数据 → 提示「检测到本地数据丢失，可从 X 月 X 日的备份恢复」并提供一键恢复。
- 没有这道检查，用户可能几个月后打开才发现账本空了，而且分不清哪次备份是好的。

**c) 导出**

- `.sqlite`：完整数据库，恢复最完整。
- `.xlsx` / `.csv`：可用 Excel 直接打开，便于用户自己查看与长期存档。
- 两种格式都要支持（成本很低）。
- 导出 CSV 时注意编码，避免 Excel 打开中文乱码（UTF-8 BOM 或 GBK）。

**d) 界面可见的备份状态**

- 直接在主界面显示**「距上次成功备份多少天」**，不要藏在设置里。
- 超过一定天数（如 30 天）给出提示。

**e) 其他**

- 启动时申请 `navigator.storage.persist()` 持久化存储权限，未获得时明确告知用户风险。

## 4. 明确不做的事

以下内容经过讨论后被**主动排除**，实现时不应擅自加入：

| 不做 | 原因 |
| --- | --- |
| 微信 / 支付宝账单导入 | 用户选择全部手输；账单格式不可控、去重与商户归类规则复杂且难以验证 |
| 多设备同步 | 纯个人单机使用 |
| 账户余额、转账、复式记账 | 只记流水。约定「不记转账」，否则统计口径会变得复杂 |
| 周期性账单自动生成 | 数据量小，手输足够 |
| 图表库、饼图 | 表格加百分比条更易读 |
| 多币种、标签系统 | 无此需求 |
| 加密货币、资产总览 | 无此需求 |

## 5. 第二阶段功能（先不做，但设计时需预留）

**分类月度预期花销 + 月底对比：**

- 为每个分类设定月度预期金额。
- 月底（或任意时刻）对比实际与预期：分类、预期金额、实际金额、差额、是否超支。
- 预期值应支持**复制上月设置**，否则每月重设会让人放弃使用。
- 超支提示要克制：用颜色或标记指出即可，**不要弹窗报警**。学生的生活费本来就有波动，过度报警会让人弃用这个工具。
- 「平均每天可用」这个指标会用到预期总额（见 3.5），因此数据模型需要提前为「月度预期」留位置。

## 6. 技术约束与已知陷阱

以下均已在现有实现中踩过或验证过，实现时必须遵守。

### 6.1 技术栈（现有实现）

- Vite 8 + React 19 + TypeScript 7（严格模式，开启 `noUncheckedIndexedAccess`、`exactOptionalPropertyTypes`）
- SQLite 使用 `@sqlite.org/sqlite-wasm`，采用官方 **`opfs-sahpool` VFS**
- 代码位于仓库的 `ledger/` 子目录

### 6.2 必须遵守的约束

| 约束 | 原因 |
| --- | --- |
| **数据库必须跑在专用 Web Worker 中** | OPFS 的同步访问句柄 `FileSystemSyncAccessHandle` 只在专用 Worker 中可用，主线程拿不到。这是硬性限制，不是架构偏好 |
| **主线程只能通过客户端模块调用数据库** | 不要在 React 组件里直接用 SQLite |
| **使用 `opfs-sahpool` VFS** | 它不需要 COOP/COEP 响应头（默认的 `opfs` VFS 需要 SharedArrayBuffer，因而需要跨源隔离）。代价是同一时间只允许一个连接，第二个标签页打开会失败——对单用户本地使用无影响 |
| **绝不能设置 `clearOnInit: true`** | 官方 sahpool 演示里设成了 `true`，那会导致**每次刷新页面清空数据库**。这是最容易踩的坑 |
| **Vite 端口固定为 5173（dev 与 preview 一致）** | OPFS 按「协议 + 主机 + 端口」隔离，换端口等于换一个空数据库，会让用户以为数据丢了 |
| **Worker 使用 ES module 格式** | 需设置 `worker: { format: 'es' }` 以匹配 `new Worker(url, { type: 'module' })` |
| **`optimizeDeps.exclude` 排除 sqlite-wasm 包** | 该包自带 `.wasm` 加载逻辑，交给 Vite 预打包会出问题 |

### 6.3 环境特殊性

- 仓库根目录同时是 DSH 的工作区，`dsh-home/` 含凭据与会话数据，**已在 `.gitignore` 中排除，不得纳入版本控制**。
- 在 DSH 沙箱内 Vite 无法启动：Vite 在 Windows 上做路径校验时会 spawn 子进程且未捕获失败，受限沙箱下直接以 `EPERM` 中断。需在项目目录下用自己的终端运行。
- 本机 pnpm 11.7.0 使用默认隔离式布局创建链接时会抛 `Maximum call stack size exceeded` 并留下悬空链接，导致 `vite` / `tsc` 无法启动。已在 `pnpm-workspace.yaml` 中改用 `nodeLinker: hoisted` 绕开。
